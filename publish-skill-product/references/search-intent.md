# Search from the job, not only the product name

Use this when researching comparable skills, improving a product page, or monitoring
discovery. Start from the selected skill's actual input, outcome and limits. Reuse
the current source/query record instead of rebuilding a keyword list each run.

## Four distinct questions

| Layer | What it checks | Example candidate |
|---|---|---|
| Name | Can someone who already knows the product find it? | `context-budget m1nga` |
| Function | What tools perform this task? | `reduce coding agent context tokens` |
| Problem | What outcome is the person trying to reach? | `AI agent avoid rereading unchanged files` |
| Pain | How does the failure appear in the person's words? | `AI agent keeps rereading same files` |

These are authored query candidates, not customer quotations. Call a phrase a user
quote only after reading the original issue, discussion or supplied feedback. Keep
its URL, date and context. Historical posts found today are not new demand today.

For unknown-user discovery, omit the owner and skill name. Add the concrete object
or environment when ambiguity pollutes results: `resume moved task folder` can
retrieve operating-system processes; `AI agent project handoff move folder` better
describes the intended job. Adding `skill` is useful for comparable implementations,
but would exclude people who only know their problem. Use their relevant language;
Xiaohongshu research may need Chinese queries even when product copy is English.

## Run, inspect, then refine

1. Read the current query set and previous successful observations. Group genuinely
   equivalent jobs so one search can serve several products; retain the mapping.
2. Run the fixed queries on the appropriate surfaces: GitHub for implementations,
   general web for discovery, a skill directory for listing visibility, and public
   issues or communities for questions. No one surface proves the others.
3. Inspect the relevant original author files and discussions. Separate a useful
   implementation, a provider's explanation, an actual user report, marketing copy
   and an unrelated result. Record no useful result as a valid finding.
4. Keep the strongest query; repair an ambiguous one by adding the task's object,
   environment or failure. Record the replacement without erasing the old result.
   Freeze the chosen query for later comparisons. Stop expanding when additional
   variants no longer change the product decision or expose a missing source.
5. Map the finding to real capability: supported, partly supported, outside scope,
   or unverified. Change the page only when it can provide a useful answer, example
   or boundary. Do not add every synonym to the trigger description or create an
   invented FAQ to fill a keyword list.

For example, a playlist's catalog identity check addresses one source of wrong
recording selection. It cannot establish that another service imported the exact
version. Make the destination check visible rather than promising perfect transfer.
Likewise, a simulated trigger audit cannot certify real harness selection.

## Keep a small, honest record

Per query retain: product/task mapping, layer, exact query, surface, observed date,
result URLs, relevance decision, source date when available, own-product appearance,
and the concrete content or workflow decision. A useful implementation source also
needs an adopt/adapt/reject decision. Volume, traffic attribution and AI citations
stay unknown without their own evidence. Search-result position is specific to the
observed engine, query and window; it is not a universal rank.

For recurring monitoring, first collect publication changes across the entire
agreed repository scope. Compare stable IDs and versions in code, then read changed
material. Preserve each source's last successful cursor on failure. A partial scan
must not erase prior records or become a claim of no activity. Treat the initial
inventory as a baseline, not as today's new events. Keep public source edits and
outreach outside a read-only monitoring run unless separately authorized.

## Research applied

On 2026-11-10, adapted seed generation, search intent and topic-to-page mapping from
[WesleySmits's keyword research skill](https://github.com/WesleySmits/agent-skills/blob/main/.agent/skills/seo-keyword-research/SKILL.md).
Retained evidence-led questions from
[Corey Haines's content strategy](https://github.com/coreyhaines31/marketingskills/blob/main/skills/content-strategy/SKILL.md).
Rejected invented search volume, fixed scoring formulas, page-length quotas and
keyword stuffing. These methods help structure an experiment; they do not prove
ranking improvements or demand for a particular skill.
