# Reviewing past requests

Only use this when the user asks for historical counts or a workflow retrospective.
Read available messages through supported tools or an authorized local read-only
history source. Do not wake tasks or change their settings to audit them.

Define the corpus, date range and counting unit before reporting numbers. Search
both explicit phrases and equivalent requests, then review the original request
and relevant response/feedback. Keyword hits are candidates, not findings.
Exclude injected rules, tool text, scheduled triggers, assistant quotations and
inherited/copied messages. Preserve separate occasions when the user actually
repeated the request. Deduplicate using provenance; disclose ambiguous copies.

Keep request frequency separate from outcomes. Repeated demands within one task
are not independent trials. At minimum distinguish explicit user acceptance,
partial acceptance with further correction, explicit challenge/rework, and an
unknown outcome. Plan approval, silence and an assistant saying “done” do not prove
user satisfaction. Normal new scope and a necessary human login are not failures.
An initial correction can evidence a prior failure; label its timing accurately.

Keep private request excerpts, dates, source/turn IDs, inclusion decisions and
outcome evidence in the existing task record. Redact credentials before displaying
or retaining excerpts; do not copy a full private archive into a public skill.
Report verified counts within coverage, not an invented all-time success rate.
Use the findings to change a small number of behaviors and test relevant boundary
cases. A historical review is not evidence that the new skill already works.
