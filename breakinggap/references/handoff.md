# A thought can become a focused conversation

Use this after the person wants a separate chat. Keep the visible synthesis brief; expand only enough to make the next conversation useful without the original transcript.

## Prepare the relevant context

Include, in natural prose or a short block:

1. The one question to explore and the desired mode: reflection, comparison, investigation, or a specifically authorized action.
2. The user's thought, attributed accurately. Keep a short exact phrase when it carries their meaning. Label your own possible interpretation separately.
3. The project purpose, known current stage, relevant evidence/source locations and unresolved constraints. State missing or uncertain context. Don't paste all chats or unrelated personal details.
4. Existing decisions, pauses, ownership or other boundaries that the next chat must preserve.
5. A useful first move. For exploration, examine possibilities with the user; do not begin implementing a newly imagined feature as if it had been approved.

If the thought is unrelated to the project, say so and omit unnecessary project detail. The person can change the scope before transfer. A visible summary is not a saved file; say “prepared” rather than “saved” until a write has actually succeeded.

## Use the host honestly

- Ask to open the specific focused chat only after showing what will carry over. An explicit request to open it after seeing that scope supplies consent; don't ask the same permission twice. If the user asks to prepare only, supply the starter without opening anything.
- Discover the native chat/thread tool and its current schema. In Codex, use the available `create_thread` capability and its placement/settings rules. Elsewhere, use an equivalent supported host feature if one exists. The skill itself cannot create windows.
- Preserve relevant user-selected model/settings and project scope under host rules. Don't create a worktree, clone a project, route to a different provider, or add a watcher just to open a conversation.
- Call creation once. Report a ready chat only with the returned identifier/link. If the host reports setup in progress, say that; don't invent a ready result. If the outcome is uncertain, use a supported read-only status check on the returned identifier if available; do not retry blindly and duplicate chats.
- If no supported creation tool exists or creation fails, keep the prepared prompt visible and explain the limitation. Never claim that a clipboard copy, a helper agent, or an unverified UI shortcut is a new user chat.
- If the user declines, returns to their agent, or only wanted an insight, stop. Don't put the idea in a backlog, schedule a reminder, or create a file without authorization.

## Illustrative starter

> Explore whether a photo community can make silent browsing feel like complete participation. This is a product question to examine, not approval to change the signup flow.
>
> The maker's reflection: “I don't want participation to feel like homework.” The project currently has signup implementation running; the available context says visitors should feel welcome even if they never post. We do not yet have user evidence that removing reactions would help. That was a possible connection, not the maker's decision.
>
> Begin by comparing what welcome could mean for a quiet visitor, and identify one uncertainty worth investigating. Preserve the current implementation until a change is requested. Relevant project records: [include actual accessible source locations, or state that none were supplied].

This example is fictional. Replace it with the person's actual thought and source context; don't copy its facts into a real handoff.
