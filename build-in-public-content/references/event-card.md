# Event card

Reuse the project's existing record. Include only fields that support the current output; this is a mapping guide, not a new database or publishing API.

- Identity: existing event ID, responsible owner, related earlier post/receipt.
- Evidence: source location, source date and exact version; the relevant passage or observed behavior.
- Claims: proposed wording paired with its support; stage and environment; limits that affect the reader's next action.
- Assets: original screenshot/footage or illustration source, edit/export version, rights/privacy checks, visual sizes actually inspected and playback result if applicable.
- Review: selected copy and visual versions; component approvals; complete-composition approval or specific hold; rejected versions and why.
- Publication: draft, held, submitted-unknown, or verified-published; permission source; platform/account; verified URL and independent receipt. An internal status label is not itself proof of permission or platform success.
- Next action: one concrete dependency or recovery step. If paused, retain the event without releasing it or advancing an unprocessed source cursor.

Example, fictional and not a publication:

Event demo-nav-02. Source: revision demo-r12, local acceptance note dated 2026-01-15. A local private prototype now opens a topic discussion from a project card; staging and production were not tested. Draft: “In our private prototype, project cards now open their topic discussions. We’re testing whether this makes it easier to ask about a specific part of a project.” Second sentence is the team's declared next test, not a result. No screenshot or recording supplied. Output is text plus a shot plan. Publication held for review; no submission or public URL.
