# Build in public content

Produce a reviewable update that lets a stranger understand what changed and why it matters. Work from the project's current evidence and brand assets. This skill does not start monitoring, recording, scheduling, or publishing.

## Find one real event

Read the current owner record, applicable holds, and publication receipts before choosing an event. Prefer the project's existing incremental comparison; inspect changed sources and necessary original passages instead of rereading the whole project. Keep its existing event ID and owner. If another channel already covered the same event, reuse its receipt or propose a genuinely different, supported follow-up.

Pick a change the audience can understand: a concrete decision, rejected approach, implemented behavior, observed failure, verification result, or open question. A code commit proves a change was committed; it does not prove a usable feature or deployment. Separate proposed, implemented, tested, private preview, and publicly available. Use the narrowest stage supported by the source, recording environment and version. Preserve new unprocessed evidence if paused or blocked; do not acknowledge away pending work.

Use the compact [event card](references/event-card.md) when a durable record is needed. Reuse existing fields rather than building a parallel ledger. If there is no worthwhile new event, record the specific gap; a posting target supplies no new facts.

## Make the update understandable

Lead with the actual action or problem and its practical consequence. A useful shape is a concrete change plus the reason it affects someone, followed by a question only if the answer can influence a real decision. Use the supplied voice and language. Distinguish translated summaries from original quotations. Keep real uncertainty, creator attribution, and verified participation boundaries.

Edit out broad significance, invented audience requests, generic enthusiasm, and conclusions that repeat the opening. Compare the final copy against the source: every new number, actor, causal claim, and availability claim needs support. Do not manufacture a personal reaction to make the writing feel human. Preserve user-approved wording; if a necessary factual correction conflicts with it, flag that conflict instead of silently treating the old approval as current.

## Choose a useful visual

Use the medium that explains this event. Text alone can explain a decision. An authentic screenshot can show a changed interaction. A comparison must label versions and comparable states. A short demonstration should show a real task and its observable outcome; when no footage exists, deliver a shot plan and state that recording has not occurred.

For branded artwork, inspect current official assets, typography, and approved examples before choosing a treatment. Preserve the supplied logo rather than redrawing it. Track approvals separately for background, wording, layout, and complete composition: approval of one component does not approve the whole image. Refine within the established visual language unless a redesign is explicitly requested. A generated illustration is not product evidence.

Make the caption state what is happening. Image text may carry a shorter phrase or an emphasized keyword when that matches the brief; it must not contradict or obscure the concrete message. Do not force every image into a universal slogan template.

Render and inspect the composition at export size and its intended feed thumbnail size. Check legibility, cropping, contrast, recognizable identity, and alt text. Report exactly which sizes were viewed. If rendering or viewing is unavailable, mark visual verification incomplete. For video, check the exported playback and captions; label staged data and later recordings accurately. Limit capture to the authorized project surface and remove private information.

## Deliver with a recoverable state

Return the finished copy, the actual visual or clearly labeled shot plan, source/version pointers, current stage, and unresolved checks. Keep rejected alternatives with their reason in the existing private task record, outside public deliverables.

Keep content quality, owner approval, and publication permission separate. A ready draft does not clear a preview hold or resume paused business. When publishing is separately authorized, check the actual account and event receipts before submission. Verify the resulting URL, account, copy, media version, and required native mentions independently. An uncertain submission goes to read-only reconciliation, never an automatic resend. Do not backfill missed schedule slots. Record the result where the original owner can resume it.
